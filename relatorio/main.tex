\begin{resumo}

Este relatório técnico apresenta o desenvolvimento de um \textit{chatbot} acadêmico capaz de
responder, em linguagem natural, perguntas sobre a base educacional do INEP/Censo Escolar. A
solução utiliza o serviço de IA generativa \textbf{Amazon Bedrock} (modelo \textit{LLaMA 4 Scout})
exclusivamente como \textbf{classificador de intenções}, devolvendo um JSON controlado, enquanto a
execução das consultas é realizada por \textbf{funções Python seguras e somente leitura} sobre um
banco \textbf{PostgreSQL}. O sistema inspeciona a estrutura real das tabelas, descobre os
relacionamentos a partir das chaves estrangeiras (sem inventar chaves) e consolida o escopo
definido pelo docente em uma consulta/visão denominada \texttt{vw\_escopo\_ia}. A interface é
construída em \textbf{Streamlit}. São discutidas a arquitetura, as decisões de segurança contra
injeção de SQL, as dificuldades encontradas e os resultados obtidos com dados reais do Censo
Escolar de 2025.

\vspace{\onelineskip}

\noindent
\textbf{Palavras-chave}: chatbot. inteligência artificial generativa. amazon bedrock. censo escolar. linguagem natural. postgresql.

\end{resumo}

\chapter{Introdução}

A consulta a grandes bases de dados governamentais, como as do Instituto Nacional de Estudos e
Pesquisas Educacionais Anísio Teixeira (INEP), normalmente exige conhecimento técnico de SQL e da
modelagem das tabelas. Isso cria uma barreira para usuários não especialistas que desejam apenas
obter informações como o total de matrículas por região ou a distribuição de estudantes por
raça/cor.

Os avanços recentes em Inteligência Artificial Generativa permitem traduzir a intenção de perguntas
escritas em linguagem natural para ações estruturadas. Este projeto emprega o Amazon
Bedrock~\cite{aws_bedrock} para interpretar perguntas e um conjunto de funções Python seguras para
executar as consultas, conciliando usabilidade (linguagem natural) e segurança (a IA nunca executa
SQL).

\section{Objetivo Geral}
Desenvolver um \textit{chatbot} com IA generativa, integrado ao Amazon Bedrock e conectado a um
banco de dados educacional, capaz de responder perguntas em linguagem natural sobre dados do
INEP/Censo Escolar, respeitando o escopo de tabelas e variáveis definido pelo docente.

\section{Objetivos Específicos}
\begin{enumerate}[itemsep=2pt]
  \item Conectar o projeto Python ao Amazon Bedrock.
  \item Conectar o projeto Python ao banco de dados PostgreSQL.
  \item Identificar, por introspecção, a estrutura real das tabelas indicadas.
  \item Realizar a junção entre as tabelas \texttt{inep\_censo\_escolar}, \texttt{municipio},
        \texttt{unidade\_federacao} e \texttt{regiao}.
  \item Criar/validar uma consulta consolidada (visão) \texttt{vw\_escopo\_ia}.
  \item Permitir perguntas em linguagem natural e interpretá-las via Bedrock.
  \item Executar consultas seguras (somente leitura) e retornar respostas claras.
  \item Construir uma interface simples em Streamlit.
  \item Documentar o projeto neste relatório técnico.
\end{enumerate}

\section{Justificativa}
O projeto justifica-se por três frentes. Do ponto de vista \textbf{educacional}, democratiza o
acesso a indicadores do Censo Escolar para gestores, pesquisadores e estudantes sem exigir domínio
de SQL. Do ponto de vista \textbf{técnico}, demonstra um padrão arquitetural seguro de integração
entre Modelos de Linguagem (LLMs) e bancos de dados, no qual o modelo apenas classifica a intenção e
o código executa consultas validadas, mitigando riscos de injeção de SQL. Do ponto de vista
\textbf{acadêmico}, exercita conceitos de IA generativa, modelagem dimensional, introspecção de
esquemas e boas práticas de engenharia de software.

\chapter{Fundamentação Teórica}

\section{Chatbots}
\textit{Chatbots} são sistemas que conversam com usuários em linguagem natural. Os de geração mais
recente apoiam-se em LLMs para compreender intenção e gerar respostas, superando abordagens baseadas
apenas em regras fixas.

\section{Inteligência Artificial Generativa}
A IA generativa baseia-se em redes \textit{Transformer}~\cite{vaswani2017attention}, capazes de
modelar dependências de longo alcance em texto. LLMs como a família \textit{LLaMA}~\cite{llama} são
treinados para prever o próximo \textit{token} e, com instruções adequadas (\textit{prompt
engineering}), podem ser direcionados a tarefas específicas, como a classificação de intenções.

\section{Amazon Bedrock}
O Amazon Bedrock~\cite{aws_bedrock} é um serviço gerenciado da AWS que oferece acesso, via API, a
modelos de fundação de diversos provedores. Neste projeto utilizou-se o modelo
\texttt{us.meta.llama4-scout-17b-instruct-v1:0} por meio da \textit{Converse
API}~\cite{aws_bedrock_converse}, com \textit{fallback} para \texttt{invoke\_model}. O acesso é
autenticado pelo AWS IAM Identity Center (SSO).

\section{Bancos de Dados Relacionais e Modelagem Dimensional}
Bancos relacionais organizam dados em tabelas relacionadas por chaves primárias e estrangeiras. A
modelagem dimensional separa \textbf{tabelas-fato} (medidas, como a quantidade de matrículas) de
\textbf{tabelas-dimensão} (atributos descritivos, como o nome do município). Esse padrão orienta a
junção realizada neste trabalho.

\section{Linguagem Natural Aplicada à Consulta de Dados (NL2SQL)}
A tradução de linguagem natural para consultas estruturadas é tema clássico de
pesquisa~\cite{zhong2017seq2sql,yu2018spider}. Em vez de gerar SQL livremente com o LLM (o que é
arriscado), adotou-se uma estratégia de classificação de intenção: o modelo escolhe uma ação dentre
um conjunto fixo e seguro, e o SQL é montado por código auditável.

\section{Dados Educacionais: INEP e Censo Escolar}
O Censo Escolar~\cite{inep_censo} é o principal levantamento estatístico da educação básica
brasileira, coletado anualmente pelo INEP. Contém variáveis sobre escolas, matrículas, docentes e
infraestrutura, servindo de base para políticas públicas e indicadores educacionais.

\section{Segurança na Geração de Consultas}
A injeção de SQL figura entre as principais vulnerabilidades de aplicações~\cite{owasp2021}. As
defesas adotadas neste trabalho incluem: separação entre interpretação (IA) e execução (código),
consultas parametrizadas, \textit{allowlist} de tabelas, validação de identificadores contra o
esquema real e transações somente leitura.

\section{Metodologia}
O desenvolvimento seguiu as etapas: (i) configuração do acesso ao Amazon Bedrock e ao banco;
(ii) inspeção da estrutura real das tabelas do escopo; (iii) descoberta dos relacionamentos por

(v) implementação das funções seguras de consulta; (vi) integração com o Bedrock como classificador
de intenções; (vii) construção da interface em Streamlit; e (viii) testes automatizados e validação
com dados reais.

\section{Processo de Junção das Tabelas}
\label{sec:juncao}

\subsection{Inspeção da Estrutura Real}
Antes de qualquer junção, o sistema inspecionou a estrutura real do banco (PostgreSQL 17.4,
\textit{host} \texttt{bigdata.dataiesb.com}, base \texttt{iesb}, esquema \texttt{public}). A
inspeção revelou um achado importante: as variáveis de matrícula (\texttt{QT\_MAT\_*}) não estão em
\texttt{inep\_censo\_escolar} (302 colunas), mas na tabela-detalhe
\texttt{inep\_censo\_escolar\_matricula} (237 colunas), relacionada à fato por
(\texttt{nu\_ano\_censo}, \texttt{co\_entidade}). Já as variáveis \texttt{TP\_*} estão na própria
tabela \texttt{inep\_censo\_escolar}. Por isso, a tabela de matrículas foi incorporada à junção,
para que o escopo do professor fosse plenamente atendido.

\section{Criação da VIEW \texttt{vw\_escopo\_ia}}
A consulta consolidada reúne o nome do município, da UF e da região, além das variáveis do escopo. O
Código~\ref{lst:view} mostra o SELECT gerado automaticamente pelo sistema.

\begin{lstlisting}[language=SQL, caption={Definição da visão vw\_escopo\_ia.}, label=lst:view]
CREATE OR REPLACE VIEW vw_escopo_ia AS
SELECT
  m.nome_municipio              AS nome_municipio,
  u.sigla_uf                    AS sigla_uf,
  u.nome_uf                     AS nome_uf,
  r.nome_regiao                 AS nome_regiao,
  f.tp_categoria_escola_privada AS tp_categoria_escola_privada,
  f.tp_localizacao              AS tp_localizacao,
  f.tp_localizacao_diferenciada AS tp_localizacao_diferenciada,
  mat.qt_mat_inf                AS qt_mat_inf,
  mat.qt_mat_fund               AS qt_mat_fund,
  mat.qt_mat_med                AS qt_mat_med,
  mat.qt_mat_bas_fem            AS qt_mat_bas_fem,
  mat.qt_mat_bas_masc           AS qt_mat_bas_masc,
  mat.qt_mat_bas_nd             AS qt_mat_bas_nd,
  mat.qt_mat_bas_branca         AS qt_mat_bas_branca,
  mat.qt_mat_bas_preta          AS qt_mat_bas_preta,
  mat.qt_mat_bas_parda          AS qt_mat_bas_parda,
  mat.qt_mat_bas_amarela        AS qt_mat_bas_amarela,
  mat.qt_mat_bas_indigena       AS qt_mat_bas_indigena
FROM inep_censo_escolar f
LEFT JOIN inep_censo_escolar_matricula mat
       ON mat.nu_ano_censo = f.nu_ano_censo AND mat.co_entidade = f.co_entidade
LEFT JOIN municipio          m ON f.co_municipio = m.codigo_municipio_dv
LEFT JOIN unidade_federacao  u ON m.cd_uf        = u.cd_uf
LEFT JOIN regiao             r ON u.cd_regiao    = r.cd_regiao;
\end{lstlisting}

\subsection{Visão Física x Visão Lógica}
O usuário de banco disponibilizado (\texttt{data\_iesb}) possui acesso somente leitura: a tentativa
de criar a visão física resultou em \texttt{permission denied for schema public}. Para contornar a
limitação sem perder funcionalidade, o sistema opera por padrão em modo \textbf{visão lógica}: a
mesma definição do Código~\ref{lst:view} é utilizada como subconsulta, mantendo o comportamento
100\% somente leitura. Caso o projeto seja executado com um usuário que tenha permissão de escrita,
a visão física é criada automaticamente. Essa decisão, além de pragmática, reforça a postura de
segurança do sistema.

\section{Tecnologias Utilizadas}
\begin{itemize}[itemsep=1pt]
  \item Python 3.12;
  \item Streamlit~\cite{streamlit} --- interface web;
  \item Amazon Bedrock~\cite{aws_bedrock} via boto3~\cite{boto3};

\section{Integração com o Amazon Bedrock}
A autenticação usa o IAM Identity Center (SSO): no primeiro uso, o navegador abre para login e as
credenciais temporárias ficam em cache (cerca de 8 horas). A região do \texttt{bedrock-runtime} é
configurável (padrão \texttt{us-east-2}); o login SSO ocorre em \texttt{us-east-1}. O \textit{prompt}
de sistema instrui o modelo a retornar apenas JSON, escolhendo uma ação de uma lista fixa
(Código~\ref{lst:prompt}).

\begin{lstlisting}[caption={Trecho do prompt de sistema (classificador de intenções).}, label=lst:prompt]
Você é um classificador de intenções para um chatbot acadêmico conectado a um
banco de dados educacional do INEP/Censo Escolar.
Sua ÚNICA função é interpretar a pergunta e retornar um JSON válido.
NÃO gere SQL. NÃO explique. Escolha UMA ação da lista permitida.
Quando o usuário falar em "a base", "censo escolar", "INEP" ou "matrículas",
considere a base final vw_escopo_ia.

Formato de saída:
{ "acao": "...", "tabela": "...", "coluna": "...", "filtro": "...", "limite": null }
\end{lstlisting}

Para a pergunta \textit{``Quantas matrículas existem no ensino fundamental por UF?''}, o modelo
retorna:

\begin{lstlisting}
{ "acao": "total_matriculas_por_uf", "tabela": "vw_escopo_ia",
  "coluna": "QT_MAT_FUND", "filtro": null, "limite": null }
\end{lstlisting}

\section{Conexão com o Banco de Dados}
A conexão é feita via SQLAlchemy, montando a URL a partir de variáveis de ambiente (arquivo
\texttt{.env}), o que mantém as credenciais fora do código. O sistema é agnóstico ao SGBD
(PostgreSQL, MySQL ou SQLite). A introspecção utiliza o \textit{inspector} do SQLAlchemy para listar
tabelas, colunas, chaves primárias e estrangeiras.

\section{Funções Implementadas}
As funções de metadados (\texttt{database.py}) incluem \texttt{conectar\_banco},
\texttt{listar\_tabelas}, \texttt{contar\_colunas}, \texttt{listar\_colunas},
\texttt{contar\_registros}, \texttt{descrever\_tabela}, \texttt{mostrar\_amostra},
\texttt{identificar\_chave\_primaria}, \texttt{identificar\_relacionamentos},
\texttt{validar\_tabela} e \texttt{validar\_coluna}. As funções do escopo educacional incluem
\texttt{inspecionar\_tabelas\_escopo}, \texttt{identificar\_chaves\_relacionamento},
\texttt{criar\_ou\_validar\_view\_escopo\_ia}, \texttt{listar\_variaveis\_escopo}, as consultas de
total de matrículas por município/UF/região, por etapa de ensino, por gênero, por raça/cor, a
distribuição por localização, os valores distintos e o resumo estatístico.

\section{Consulta Livre em Linguagem Natural (NL$\rightarrow$SQL)}
Além das ações estruturadas (determinísticas) do escopo, o sistema possui um modo
\textbf{NL$\rightarrow$SQL} que permite responder \textbf{qualquer} pergunta sobre os
\textbf{dados das tabelas do escopo}. Quando a pergunta não corresponde a uma ação
pré-definida, o classificador retorna a ação \texttt{consulta\_sql} e o fluxo passa a
ser: (i) o Bedrock recebe o esquema da base consolidada \texttt{vw\_escopo\_ia} e gera
um comando \texttt{SELECT}; (ii) o Python valida que se trata de uma consulta somente
leitura e que ela referencia apenas tabelas do escopo (\textit{allowlist}); (iii) como a
\textit{view} é lógica, ela é injetada como CTE e a consulta é executada; (iv) o Bedrock
resume o resultado em linguagem natural. Assim, perguntas como \textit{``Qual a média de
matrículas do ensino médio por município em Goiás?''} são respondidas dinamicamente,
enquanto perguntas fora do escopo (ex.: PIB, acidentes) são recusadas. Esse modo pode ser
desativado (\texttt{PERMITIR\_SQL\_LIVRE=false}) ou ampliado para todo o banco
(\texttt{PERMITIR\_TODAS\_TABELAS=true}) via variáveis de ambiente.

\section{Fluxo de Funcionamento do Chatbot}
\begin{enumerate}[itemsep=1pt]
  \item O usuário digita a pergunta na interface.
  \item \texttt{chatbot.py} envia a pergunta ao Bedrock.
  \item O Bedrock devolve o JSON de intenção (ação + parâmetros).
  \item O JSON é normalizado e validado contra a lista de ações permitidas.
  \item A função segura correspondente em \texttt{database.py} é chamada.
  \item O resultado é formatado (texto + tabela) e exibido ao usuário.
\end{enumerate}

\section{Dificuldades Encontradas}
\begin{itemize}[itemsep=2pt]
  \item \textbf{Variáveis em duas tabelas:} as \texttt{QT\_MAT\_*} não estavam na tabela principal,
        e sim em \texttt{inep\_censo\_escolar\_matricula}; resolvido incorporando essa tabela à junção.
  \item \textbf{Acesso somente leitura:} não foi possível criar a visão física; adotou-se a visão
        lógica (subconsulta equivalente).
  \item \textbf{Saída do LLM:} modelos abertos podem incluir texto extra junto ao JSON; implementou-se
        extração robusta do primeiro bloco JSON balanceado e \textit{fallback} para
        \texttt{pergunta\_nao\_suportada}.
  \item \textbf{Maiúsculas/minúsculas:} divergência entre o escopo (nomes em maiúsculas) e o banco
        (minúsculas), tratada por resolução \textit{case-insensitive} e \textit{quoting} de identificadores.
  \item \textbf{Valores já textuais:} colunas como \texttt{TP\_LOCALIZACAO} retornam ``Urbana''/``Rural''
        (texto), exigindo rotulagem condicional.
\end{itemize}

\section{Resultados Obtidos}
O chatbot respondeu corretamente, com dados reais, a perguntas de metadados e do escopo educacional.
A base consolidada possui 18 colunas e abrange 214.192 escolas (Censo 2025). As agregações por
região, UF, etapa, gênero e raça/cor foram validadas. A separação entre interpretação (IA) e
execução (código) mostrou-se eficaz, segura e de fácil manutenção.

\section{Limitações do Projeto}
\begin{itemize}[itemsep=1pt]
  \item O conjunto de perguntas é limitado às ações pré-definidas (não há SQL livre).
  \item Filtros compostos (ex.: ``matrículas no Sudeste em escolas rurais'') ainda são limitados.
  \item Depende de credenciais válidas de AWS/SSO e de conectividade com o banco remoto.
  \item A qualidade da classificação depende do modelo de fundação utilizado.
\end{itemize}

\section{Possibilidades de Melhoria}
\begin{itemize}[itemsep=1pt]
  \item Suporte a filtros combinados (UF + localização + etapa) na intenção.
  \item Geração de gráficos automáticos na interface.
  \item Cache de respostas e memória de contexto conversacional.
  \item Avaliação quantitativa da acurácia de classificação de intenções.
  \item Exportação de resultados (CSV/Excel) e \textit{logging} de auditoria.
\end{itemize}

\chapter{Conclusão}

O projeto atingiu os objetivos propostos: um chatbot funcional, integrado ao Amazon Bedrock e
conectado a um banco PostgreSQL real, capaz de responder em linguagem natural a perguntas sobre o
INEP/Censo Escolar, dentro do escopo definido pelo docente. A arquitetura adotada --- IA apenas para
interpretar a intenção e código auditável para executar consultas seguras --- equilibra usabilidade
e segurança, constituindo um padrão replicável para integração entre LLMs e bancos de dados. As
dificuldades reais encontradas (variáveis em duas tabelas e acesso somente leitura) foram
contornadas de forma documentada, reforçando o caráter prático e seguro da solução.
